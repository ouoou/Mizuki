# 问题

## 采购域

### 采购项目业务背景

采购项目对于不同行业不同公司，都有不同的采购模式，并且单据来源和履约方式的差异比较大，如果每个项目都单独实现一套采购流程，维护成本也高，流程标准、异常处理和对账方式也很难统一

采购业务类型可大致分为：间接采购、直接采购
间接采购可分为：计划生产物资采购单、商城来源的采购单、以销定采、调拨单、反向调拨单
直接采购可分为：运营人员直接下采购单
等模式

### 为什么单独做采购中台？

不同项目的采购细节虽然不同，但是底层都会涉及采购申请、订单、履约衔接、异常、对账等共性的能力，如果不做中台，轮子会重复建设，后续新增模式或调整规则需要改动很多代码
共性的能力由中台承接、差异化部分则通过规则引擎、流程编排实现

### 从0到1 具体什么是从0-1

从开始的采购领域建模、流程抽象、服务编排等设计开始。梳理不同采购模式 之间的共性和差异，哪些规则是需要配置的，哪些动作是需要和履约等模块进行交互，边界条件的判定。
哪些规则是需要配置的eg：审批流、是否需要供应商协同

### SRM、电商这些多源单据是怎么统一接入的？

这些外部模块需要接入采购单据，则都统一接入采购申请模块，在这个基础上，后续流程则不需要直接依赖外部系统的原始结构，而是直接从申请到生成订单，统一化流程，不需要重写采购的主流程

### 什么是服务编排引擎和规则引擎？解决了什么问题？

先讲讲服务编排
两个概念 业务链chain  执行单元action
服务编排呢就是由一个业务链多个编排的执行单元组成，规则引擎则是执行单元中的一个条件节点，通过阿里的qlExpress实现。
简单来说 服务编排主要解决怎么执行，规则主要解决怎么判断。引入它两最主要解决的是两个问题：方便二开拓展  方便日后维护

### 编排服务引擎如何实现的?

1. 我们把服务编排抽象成 chain + action，chain 是业务流程，action 是执行单元。
2. 启动时把 action 注册到组件中心，把 chain 注册到 FlowBus。
3. 运行时通过统一 executor 按 chainId 取出流程，创建上下文。
4. 然后执行器根据流程定义去调度每个单元，然后执行器会按流程定义，依次调度每个执行单元。
   如果是普通节点，就顺序执行；
   如果是 `condition` 节点，就走规则判断；
   如果是并行节点，就把多个分支同时调度；
   如果是循环节点，就按条件重复执行。
5. 其中规则引擎本质就是 condition action，通过 QLExpress 做表达式匹配，再决定后续走哪个执行单元。

### chain + action 的定义是怎么做版本管理的？流程变更后老单据走新链还是旧链？

chain action定义在代码中，跟随代码的版本一起管理

流程变更之后走的是新业务chain，如果老业务绑定的是老版本的chain，未来如果旧单据需要调用已经变更的旧的业务链，可以根据原chainId调用

### QLExpress 里的变量从哪来？如果运营配置错了变量名，怎么在发布前发现？

变量都是由开发人员定义
是由开发人员来进行配置
变量名是定义在代码中的枚举，发布前通过ide编译机制控制

### 代码注册和平台可视化编排同时存在时，优先级怎么定？
无法同时存在两个相同的业务链

### action 之间传递的是强类型对象还是 Map 上下文？
map字段类型的上下文


### 并行节点里一个 action 失败了怎么办？整条链回滚、局部补偿，还是继续执行？

基础平台的执行单元是没有做事务的控制，而是由各个业务的实现方，来控制业务是全部/局部回滚还是无视

### 为什么不只用工作流引擎？

工作流引擎适合解决流程节点的流转，但是采购里很多判断是复杂的业务规则，像工作流引擎适合做审批流任务的流转

### 为什么不用先成的流程引擎flowable、camunda？

核心主要两个原因：
1引入重型的工作流当然是可以适配我们的业务的，但是里面很多功能使用不上的，其中的业务编排和规则引擎时可用，那不如用轻量级的方式去实现自己的业务诉求
2成本问题 维护成本 服务器资源成本（甲方不一定愿意付出很多服务器资源）

### 你说工作流引擎太重，那你们自己做的引擎少了哪些能力，比如可视化、回放、历史追踪、审批态管理？

基础平台中定义的流程编排定义的其实是轻量级的，还有一个我们团队需要的，可视化信息的话是由基础域的同学提供接口，业务团队跟其接口进行对接，以此来展示当前订单到哪一步中


### 流程节点的抽象

根据通用规则 抽成更加通用的可执行的一个个单元,eg: 保存节点、提交节点、审批节点、消息提交节点、校验节点等

### 流程上下文怎么传递

采购业务链执行过程中上下文共享数据的对象 从最开始执行时的初始化 引用传递到最后一个最小可执行单元中

### 千行级采购单据为什么会超时？

超时不是单点原因，主要是配置查询、服务编排、下游调用叠加导致的

多行级别单据放大每行的规则判断
外部调用成本
同步履约的流程 导致

链路一步步拆解，先看业务chain上每个执行单元的耗时，定位到位置（1配置做预加载 减少主链路的查询 2重构业务chain 优化没必要的串行逻辑 3将非强实时的动作拆出主链路 4 捞出慢sql进行优化）
再用arthas调出火焰图，查看是否cpu占比过高存在异常

### action 之间传递的是强类型对象还是 Map 上下文

强类型对象，其中会包含自定义上下文的map，根据你自定义的名称往里塞入具体的对象

### 如果再来一个两千行单据，你现在的方案还能扛吗？

我不会直接拍脑袋说一定没问题，但按照现在这套方案，肯定比原来稳很多，不会再像之前那样因为链路过长和同步依赖直接超时。

原因是我已经把几个核心风险点处理掉了：配置查询做了预加载和缓存，编排层减少了不必要串行，下游履约做了解耦，非强实时动作摘出主链路。所以从架构上讲，它已经具备继续放大的基础。

但如果从一千行继续翻到两千行，我会明确做两件事。第一是重新压测，看瓶颈是不是重新落到规则判断放大、批量数据库操作，或者下游批处理能力上。第二是针对超大单据继续做专项优化，比如更彻底的批量化、分段处理、受控并行，必要时把超大单拆成子任务异步推进，而不是仍然要求一次请求同步走完整条链

## 会员域

### 会员项目的业务背景是什么？

会员域的目标其实是沉淀会员主数据、账户、等级，为日后的触达营促销 打基础。业务上要支撑多业态、多账户，比如积分、金币以及按账户值驱动的等级体系

### 你是如何设计领域模型的？

根据子模块来进行划分
会员主数据
会员账户
会员等级
在进行细分按照数据形态拆成配置数据/业务数据
这样后续拓展业态、类型会更加稳定

### 按照你的设计是如何扛过大促活动的？

1.会员查询账户额度，没命中走库写缓存，命中缓存走缓存，避免频繁打库
2.会员账户流水的更新，拆分大事务，会先将可用额度使用lua脚本原子更新缓存，后续发消息异步更新任务表、流水信息，慢慢进行任务的消费
3.任务失败扫任务表做一致性的补偿

### 在异步更新期间会遇到 缓存/库 不一致的情况，有没有因此发生过什么问题？

所有查询账户额度的链路 都优先从缓存中读取

确实会有短暂不一致，实际遇到过短时查旧值，但没有演变成最终资损，因为统一读缓存 + 异步重试 + 对账补偿

### 消息消费超时、网络抖动、任务重试导致重复处理你是如何解决的？

1.做好幂等键处理，幂等键相同直接返回
2.幂等键没有如果任务也没有 直接放过
3.幂等键不存在但是账户任务存在则继续判断状态

### 如何做审计追溯？

根据流水、任务记录能解释每次余额的变化


### 做会员有没有碰见过什么难点？

大促时间段后会有大批量的账户积分到期

1.设计方面为什么要把流水明细单独抽取出来，就是为了到期/扣减方便扣余额，以免出现不够扣的情况
2.之前线上我们就发现在到期任务去扫描账户表时任务处理很慢，导致任务积压严重。发现是扫表时的慢sql导致，一开始也很疑惑 明明也是有索引的，为什么会慢，拉出慢sql，发现也根据业务主键 where 查询，`order by id limit 100` 
最后发现 根本原因是：
但是我们类型code长度是（MEMEBERTYPE202510302208320）,项目上可以自定义code规则
联合索引中等级类型code长度20，真实项目上的长度是26位。导致根据这个联合索引查询查询到很多值
表面上看有条件查询、有分页，但是数据量上来后，优化器为了利用主键有序，选择了主键索引，而没有选择我设置的索引导致扫描行数很大。
解决方案
1.强制使用我设置的联合索引
2.增大联合索引中我设置的等级类型code长度

还需要有完善的对账机制，能梳理出清晰的对账路线，以免发生资损

### 会员等级是怎么实现的？

等级是事件驱动的，消费对应的事件，根据等级规则来完成等级的升降级以及保级策略

会员等级升级：订单完成后根据等级规则 增加对应的经验以及级别
会员等级保级：会员根据配置如果当前规则在保级条件内 不立即退级
会员等级降级：会员超过保级条件、进行降级

### 会员与你专利的关系是什么？

会员会与权益域关联，比如1000积分可以兑换多少个优惠券，券这里会与促销相关
之前给促销的小组帮过忙 写过一些促销的需求

那这个专利的意思是：
对于一些高客单价的商品，尤其是家电家具等大件商品，用户一次性可能购买多件商品，但是多件商品共同参与优惠时，这些商品未必能获得最大的优惠
主要是针对多件商品参与阶梯满减活动的场景，自动计算出总优惠金额最大的拆单方案
比如：
满2000-200
满4000-500
满6000-800
当某一商品超过阶梯优惠最大金额，则该商品拎出来单独成单，直接锁定一份最高档优惠
- 商品 A：7000
- 商品 B：3000
- 商品 C：2000

该订单最多命中最高档：

- 满 6000 减 800

## ai选品

### 业务背景是什么？

业务上需要将选品-铺品一套流程进行自动化，减少人工的介入筛选度。

### 如何实现的？

从选品上其基本流程分为：数据平台拉取信息->初筛-》竞品获取-》竞品分析-》寻源-》寻源分析-》ROI计算
需要大量人工参与的 初筛-竞品分析-寻源分析，这里就可以让ai介入 进行筛选。

将数据拉取进来，一个个商品分别交给ai,ai拿到数据后，先经过通用agent判断 该任务需要分配给谁，哦知道它属于初筛信息，将他交给初筛agent
**初筛分析**
初筛agent 判断是否符合我们运营人员的规则，例如涉及液体、侵权、黄、暴力等风险直接剔除，最后根据规则对 图片 标题 副标题 品类等信息进行打分 超过60分则算通过，最后将通过的信息 交给格式化agent，将筛选出来的商品信息 严格返回出我们想要的格式，最后ai自己对返回的格式进行挨个进行校验，如不满足当前的规则 则继续交给格式化agent进行修改 最大3次，最后返回。

通过初筛的商品 进行汇总，去电商平台中拉取对应的竞品信息，拉到的竞品信息 交给竞品分析agent

**竞品分析**

竞品分析agent 判断图片、标题、详情等信息匹配度, 销量趋势分析、商家分析、竞品数等信息分析，最后根据当前模型打分，超过60则通过
然后交给格式化agent 同上

通过竞品分析的商品，进行汇总，交给1688寻源，通过以图搜图 查询对应的供应链商家信息

**寻源分析**
竞品分析agent 判断卖家图片、标题、详情等信息匹配度，卖家实力身份、工厂身份、等信息分析，最后根据当前模型打分，超过60则通过
然后交给格式化agent 同上

最后计算通过的商品ROI

### 为什么这个场景适合用 AI，而不是纯规则引擎？

这里即有结构化的判断，也有主观的判断
纯硬编码 比如 数据拉取时关键信息的 缺失可以直接返回
主观的判断就交给模型比如：图片、标题 是否匹配。是否有侵权、黄、液体等风险
### 为什么要做多 agent，而不是一个大 prompt 一把梭？

1.一个大的prompt混杂在一起，容易让ai产生幻觉不稳定性
2.容易输出不稳定，模型可能在这一轮重试判断
3.出了问题很难定位，不知道是哪一个阶段出现了问题
4.成本高，如果出现问题，那全的重跑一遍，token消耗大

### AI 输出不稳定、格式不对时怎么处理

限制ai的输出结构，最后要输出时，自行校验其格式是否正确，如不正确 重试当前格式化agent

### 项目的验证以及如何判断当前系统做的好不好

取一批数据进行筛选，再跟运营人员进行审核，持续查看人工和运营人员的一致率，进行交叉验证。看最终通过的商品转正式商品的比例、后续 ROI 达标率、供应商质量，以及运营团队对结果可用性的反馈。

### 如果ai与人工意见冲突怎么兜底?

我们选品结束之后 有审核机制，各个运营人员在审核页面看到ai的结果，最终通过人工把控，运营人员提交该品的审批，交给其tl过审。

### 模型调用成本、延迟、失败率怎么控？

1.前置过滤 把硬编码规则 该过滤的过滤，不用ai分析的 自己分析掉
2.格式化，简单的操作用轻量级的模型，需要重任务复杂分析的使用更强的模型
3.控制模型重试的次数
4.控制token消耗的最大限制
5.控制当前真正需要使用到的上下文，传递给ai

### 为什么一定要做“通用 agent -> 初筛 agent -> 格式化 agent”这套结构？

主要是为了职责划分
通用agent 负责统一入口 和 任务的划分，做任务的理解和标准化
初筛agent 负责真正的业务判断
格式化agent  负责输出的稳定性

### 3 次修正后还失败怎么办？

### alibaba ttl并发下如何解决threadlocal多线程下上下文传递的问题？

父线程先将上下文会放入ttl中，提交任务时ttl会拿到当前上下文的引用，这个任务会包装成runnable，执行之前会备份原来的threadlocal值，再把父线程的上下文引用放进去，执行完之后恢复原来的备份值
