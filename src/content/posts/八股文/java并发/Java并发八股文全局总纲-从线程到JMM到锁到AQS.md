# Java并发八股文全局总纲 - 从线程到JMM到锁到AQS

这篇文档不是把 Java 并发知识点平铺展开，而是试着用**一条主线**把整个 `java并发` 目录里的内容串起来。

如果你先只记一句话，可以记这个：

> **Java 并发本质上是在解决“多个线程同时操作共享资源时，如何既正确又高效”这个问题。**

所以整套 Java 并发八股文，最终都在围绕下面几个问题打转：

1. **为什么并发会出问题**
2. **Java 怎么定义并发世界里的规则**
3. **我们用什么机制保证线程安全**
4. **这些机制在 JDK 里如何被抽象成工具**
5. **现代 Java 并发又是怎么继续演进的**

只要这五个问题串起来，Java 并发就不会看成一堆碎片。

## 一、先抓住整条主线

学 Java 并发，最怕的是把知识点一个个背散。  
更好的方式，是顺着下面这条主线往下走：

```mermaid

    A[线程为什么会出问题] --> B[Java 用 JMM 建立规则]

```

你可以把这条主线理解成：

1. 先知道并发为什么天然不安全。
2. 再知道 Java 为什么要有 JMM 这种“规则层”。
3. 再知道 `volatile`、`synchronized`、`CAS` 各自解决哪类问题。
4. 再知道 AQS 如何把这些同步能力抽象成一套统一框架。
5. 最后再看线程池、ThreadLocal、虚拟线程这些工程化和现代化方案。

## 二、入门篇：先理解 Java 并发到底在解决什么

入门阶段最重要的不是上来就背 AQS，而是先回答一个更根本的问题：

**为什么要并发？为什么并发一多就容易出事？**

### 1. 并发和并行，是整个并发世界的起点

很多并发问题，如果连“并发”和“并行”都没分清，后面就很容易糊。

- **并发**
  - 强调一段时间内多个任务交替推进
  - 不一定真的同一时刻一起跑
- **并行**
  - 强调同一时刻多个任务同时执行
  - 更依赖多核 CPU

所以 Java 并发编程，讨论的重点往往不是“有没有多个核”，而是：

> **多个执行单元会不会在逻辑上同时接触同一份共享数据。**

### 2. 线程为什么比进程更容易出并发问题

Java 程序运行在 JVM 进程中，而我们常说的 Java 并发，主要是在说多个线程之间的协作和竞争。

线程之所以容易出问题，是因为：

- 线程共享堆内存
- 线程切换是随时可能发生的
- 读、改、写往往不是一个不可分割的动作

这三点一叠加，就会出现：

- 脏读旧值
- 写覆盖
- 可见性问题
- 指令重排序带来的诡异结果

所以并发的根问题可以压缩成一句话：

> **多个线程会以不可预期的时序访问同一份共享状态。**

### 3. 上下文切换，是并发世界的隐性成本

很多初学者只看到“多线程可以更快”，但忽略了线程切换本身是有成本的。

上下文切换意味着：

- 保存当前线程执行现场
- 恢复另一个线程的执行现场
- CPU 缓存命中可能变差
- 调度本身也要消耗时间

所以 Java 并发不是“线程越多越好”，而是：

> **线程多了以后，吞吐未必上去，调度和切换成本反而可能先上来。**

### 4. 入门阶段你先记住这几个判断

- Java 并发的核心不是“让代码同时跑”，而是“让共享数据在同时跑时仍然正确”。
- 并发问题的根源是共享数据、执行交错、缓存可见性和重排序。
- 多线程不是天然提速工具，线程切换和协调本身也有成本。
- 线程安全最终离不开三件事：**原子性、可见性、有序性**。

只要这四点立住，后面再看 JMM 和锁，就不会飘。

## 三、基础篇：把 Java 并发最核心的四条主线打通

基础阶段建议把 Java 并发分成四条主线：

1. 线程与状态主线
2. JMM 主线
3. 同步原语主线
4. 抽象框架主线

### 1. 线程与状态主线：先理解并发执行体本身

#### 1.1 线程状态不是背枚举，而是为了理解阻塞在哪里

Java 线程状态常见有：

- `NEW`
- `RUNNABLE`
- `BLOCKED`
- `WAITING`
- `TIMED_WAITING`
- `TERMINATED`

真正要理解的不是把这几个名字背下来，而是：

- 线程为什么会进入这些状态
- 它到底是在等 CPU、等锁、等条件，还是等超时

因为线上排障时，很多问题最终都要落回：

- 为什么线程一直不动
- 为什么线程堆积
- 为什么锁迟迟拿不到

#### 1.2 线程安全，不是“加锁了就算”

“线程安全”这个词最容易被说空。

真正更准确的理解应该是：

> **在线程交错执行的情况下，程序行为仍然满足预期。**

所以线程安全关注的不是某个语法，而是结果是否稳定。

这件事往往要从三个维度看：

1. 单个操作是否不可分割
2. 一个线程写入的结果另一个线程能否看到
3. 多步操作之间的顺序能否被打乱

这三件事正好对应：

- 原子性
- 可见性
- 有序性

### 2. JMM 主线：Java 为什么要先定义规则

#### 2.1 JMM 是 Java 并发的规则层，不是物理内存图

很多人学 JMM 一开始容易绕进“工作内存是不是某块真实 RAM”这种问题里。

其实 JMM 更重要的理解方式是：

> **JMM 是 Java 为了屏蔽不同 CPU、缓存、编译器和运行时差异，而定义的一套并发访问规则。**

它重点不是告诉你“硬件长什么样”，而是告诉你：

- 线程之间什么时候能看到彼此修改
- 什么操作不能被随便重排
- 哪些规则可以推出 happens-before

#### 2.2 有了缓存一致性协议，为什么还需要 JMM

这也是高频题。

像 MESI 这种协议，解决的是硬件缓存一致性的一部分问题。  
但 Java 程序真正面对的，还不只有硬件：

- 编译器会优化
- JIT 会重排
- CPU 会乱序执行
- 不同平台实现不一样

所以 JMM 存在的意义是：

> **把底层复杂硬件行为抽象成 Java 程序员可以依赖的一套统一语义。**

#### 2.3 happens-before 是 JMM 最重要的落地规则

JMM 最终不是让你背概念，而是让你能判断：

- 某次写，对某次读，是否一定可见
- 某段代码执行顺序，是否一定成立

而 `happens-before` 正是这个判断工具。

所以 JMM 主线真正想让你掌握的是：

> **Java 并发里很多“到底安不安全”的判断，最后都要回到 happens-before。**

### 3. 同步原语主线：volatile、synchronized、CAS 各自解决什么

这一部分是面试最常问、也最容易混的地方。

正确理解方式不是一个个背，而是先看它们各自解决什么问题。

#### 3.1 volatile：解决的是可见性和一定程度的有序性

`volatile` 最核心的作用不是“线程安全万能药”，而是：

- 保证写入对其他线程可见
- 限制特定重排序

它适合：

- 状态标记
- 开关变量
- 双重检查锁中的引用发布

它不适合：

- 复合读改写操作
- 像 `i++` 这种需要完整原子性的逻辑

所以一句话记住：

> **volatile 解决“看得见”和“别乱排”，但不直接解决“多步操作不可分割”。**

#### 3.2 synchronized：解决的是互斥、可见性和有序性

`synchronized` 比 `volatile` 更强，因为它本质上是互斥同步。

它能同时处理：

- 临界区互斥进入
- 解锁前对共享变量的刷新
- 加锁后对共享变量的重新读取

所以它常被理解为：

> **只要临界区边界划对了，synchronized 能把原子性、可见性、有序性一起兜住。**

但也正因为如此，它的代价通常比纯 `volatile` 更大。

#### 3.3 synchronized 的底层，不是简单“加个锁”

这里真正要串起来的知识点有：

- 对象头
- `Mark Word`
- `monitorenter / monitorexit`
- 锁状态
- 锁升级

它们本质都在说明：

> **synchronized 不是一个平面的关键字，而是一整套从字节码、对象头到 monitor 实现的同步机制。**

偏向锁、轻量级锁、重量级锁这些知识点，也不是零散记忆题，而是在回答：

- JVM 如何尽量减少锁竞争成本
- 什么时候用更轻的手段
- 竞争激烈时如何升级到更重的同步方式

#### 3.4 CAS：解决的是无锁条件下的单点原子更新

CAS 这条线，应该和 `volatile`、锁放在一起比较着学。

CAS 的核心能力是：

- 比较内存中的旧值是否等于预期值
- 如果相等，就原子地更新成新值

它非常适合：

- 原子计数器
- 无锁更新
- 并发状态切换

但它也不是万能的，因为它会带来：

- ABA 问题
- 自旋开销
- 只能天然处理单点共享状态

所以正确理解是：

> **CAS 是一种偏底层、偏轻量的原子更新机制，适合竞争不激烈、临界区很小的场景。**

#### 3.5 volatile、synchronized、CAS 之间的关系

这三个点一定不要拆开学，应该放成一个选择题框架：

- 只需要可见性和禁止重排：优先看 `volatile`
- 需要临界区互斥和复合操作原子性：优先看 `synchronized` 或锁
- 需要高性能单点原子更新：优先看 `CAS` 或原子类

基础阶段到这里，要形成一个核心认知：

> **Java 并发的很多选择，不是“谁更高级”，而是谁更适合当前问题。**

### 4. 抽象框架主线：AQS 为什么是并发工具类的核心

如果说 `volatile`、`synchronized`、`CAS` 是砖头和钢筋，  
那 `AQS` 更像是并发框架里的标准地基。

#### 4.1 AQS 的定位，不是一个“知识点”，而是同步器骨架

AQS 的核心作用可以理解成：

- 用一个 `state` 表示同步状态
- 用一个队列维护获取同步失败的线程
- 提供独占和共享两种基础模式

这让很多并发工具不必从零实现等待、排队、唤醒逻辑。

所以 AQS 真正的定位是：

> **JDK 并发同步器的通用模板框架。**

#### 4.2 AQS 为什么重要

因为很多常见工具类都能挂在它下面理解：

- `ReentrantLock`
- `CountDownLatch`
- `Semaphore`
- 部分 `Condition` 能力

所以学 AQS，不是为了背源码，而是为了建立一个统一视角：

> **为什么这些并发工具看起来功能不同，底层却能复用一套排队和唤醒机制。**

#### 4.3 AQS 其实把并发问题进一步标准化了

你可以把 AQS 理解为一套统一问题模板：

1. 同步状态怎么表示
2. 抢不到资源的线程放哪里
3. 什么时候阻塞
4. 什么时候唤醒
5. 独占模式还是共享模式

这样并发工具类就不再是一个个孤立设计，而能归并到同一条线里。

## 四、进阶篇：把 Java 并发真正讲深的几个主题

基础打牢后，真正拉开差距的，是下面这些进阶问题。

### 1. AQS 工具类：从原理到工程能力

这一组工具类不要零散背，要按“用途”来归类：

- **控制互斥**
  - `ReentrantLock`
- **控制并发数量**
  - `Semaphore`
- **等待一组任务完成**
  - `CountDownLatch`
- **让一组线程互相对齐**
  - `CyclicBarrier`

它们表面功能不同，但都可以回到：

- 状态怎么变化
- 线程怎么排队
- 线程何时释放

这就是 AQS 这条线的工程价值。

### 2. 锁和 CAS 的选择，是性能与冲突特征的选择

这也是高频面试题。

真正要比较的不是“CAS 和锁谁更先进”，而是：

- 冲突概率大不大
- 临界区长不长
- 自旋是否划算
- 线程阻塞唤醒成本是否值得

通常可以这样理解：

- 竞争轻、操作短：CAS 往往更合适
- 竞争重、逻辑复杂：锁往往更稳妥

所以这道题最后其实是：

> **要根据冲突模型和临界区形态选同步策略，而不是迷信某种技术。**

### 3. ThreadLocal：并发世界里的另一条路，不是共享而是隔离

前面大多数并发知识都在解决“共享变量怎么安全访问”。  
ThreadLocal 提供的是另一种思路：

> **既然共享难，那就干脆给每个线程一份独立副本。**

这就是它的核心思想。

它很适合：

- 用户上下文
- 请求链路信息
- 线程内复用对象

但它也带来高频风险：

- 在线程池场景下容易残留旧值
- 如果不清理，容易形成内存泄漏问题

所以 ThreadLocal 的重点不是“会不会用”，而是：

- 知道它为什么能隔离
- 知道它为什么会泄漏
- 知道在线程池中必须及时 `remove`

### 4. 线程池：并发不只是同步，还包括资源调度

很多人学 Java 并发只盯着锁，其实工程里更常见的问题是：

- 线程到底怎么创建和复用
- 为什么不能无限 new Thread
- 任务来了之后谁来执行、排队、拒绝

线程池这条线，真正解决的是：

> **如何把线程从“手动创建对象”升级成“可管理的执行资源池”。**

所以线程池要理解的不是 API，而是下面这几个核心点：

- 核心线程数
- 最大线程数
- 阻塞队列
- 拒绝策略
- 线程复用

这其实是在做并发世界里的“资源调度与流量控制”。

### 5. 原子性：并发里的原子性和数据库事务原子性不是一回事

这是一个很容易混淆但很能体现理解深度的话题。

Java 并发里的原子性，强调的是：

- 某个操作对其他线程来说不可分割

数据库 ACID 里的原子性，强调的是：

- 一个事务要么全做，要么全不做

所以两者不是一回事。

这个知识点真正想提醒你的是：

> **并发里的原子性更偏“执行单元不可被打断”，数据库里的原子性更偏“业务变更集合不可部分提交”。**

### 6. 虚拟线程：现代 Java 并发的演进方向

虚拟线程这条线，最好放在最后看，因为它不是在推翻前面的知识，而是在改变并发建模方式。

虚拟线程的核心意义是：

- 让“一个任务一个线程”的编程模型重新变得便宜
- 降低传统平台线程的创建和切换成本
- 让大量阻塞式 I/O 场景更容易写出高并发代码

但它不是“并发原理失效了”，而是：

> **线程的成本模型变了，但共享数据、可见性、同步、线程安全这些根问题并没有消失。**

所以虚拟线程应该挂在这条线末端理解：

- 它优化了“线程怎么调度”
- 但并没有绕开“共享状态怎么同步”
